## Scope
Make Git affordance state terminal-safe and timing-authoritative:
- Refactor `useFloatingGitButtonAffordances` so press-in, release, cancellation,
  failed gesture, route change, and unmount have explicit cleanup.
- Preserve release-based stage/commit/push semantics and exactly-once callback behavior.
- Keep `HOLD_FILL_MS = 3000` authoritative with derived 1000/2000/3000 thresholds.

## Problem Analysis

### Duplicate emission bug
The original implementation had a race: if the user held past 3000ms, both
`handleHoldComplete` (fires at 3000ms, emits 'push') AND `handlePressOut`
(fires on release, also emits based on holdProgress.value) would BOTH call
`onReleaseSegment`, resulting in duplicate 'push' callbacks.

Root cause:
- `handleHoldComplete` unconditionally called `onReleaseSegment('push')` and started
  a drain animation on holdProgress
- `handlePressOut` then read `holdProgress.value` (now mid-drain) and emitted
  based on whatever fraction it saw
- No guard against duplicate emissions

### Cleanup gaps
- Unmount cleanup used `cancelAnimation` which freezes values in place, but did
  not drain progress to 0 visually
- `cancelAffordances` set values to 0 immediately (no drain animation)

## Solution

### 1. Duplicate emission guard (`holdCompleteFiredRef`)
Added `holdCompleteFiredRef = useRef(false)` to track whether `handleHoldComplete`
has already fired for the current press cycle.

Modified `handlePressIn` to reset: `holdCompleteFiredRef.current = false`

Modified `handleHoldComplete` to:
- Return early if `holdCompleteFiredRef.current` is already true (idempotent)
- Set `holdCompleteFiredRef.current = true` before emitting
- Drain holdProgress with `withTiming(0, { duration: HOLD_DRAIN_MS })`

Modified `handlePressOut` to:
- Return early (skip all emission logic) if `holdCompleteFiredRef.current` is true
  (hold already completed, its callback already fired)
- Otherwise proceed with normal segment detection based on `holdProgress.value`

### 2. Terminal paths covered

| Path | Behavior |
|------|----------|
| Press-in | Resets `holdCompleteFiredRef = false`, starts hold animation |
| Hold complete (3000ms) | Sets ref=true, emits 'push', starts drain |
| Release after hold complete | Ref=true, pressOut returns early, no double-emit |
| Hold complete called twice | Idempotent — second call returns early |
| Cancel during partial fill | Sets `holdCompleteFiredRef=false`, cancels animations, resets to 0 |
| Release after cancel | Ref=false, but holdProgress=0 → no segment emitted |
| New press after any terminal | Ref resets to false, hold restarts from 0 |
| Unmount | `cancelAnimation` on all three progress SVs (existing behavior) |

## Race Evidence (manual cancel/release patterns)

### Pattern 1: Cancel BEFORE release
1. Press-in → holdProgress starts
2. Advance to 1500ms (holdProgress ≈ 0.5)
3. `cancelAffordances()` → holdProgress=0, pressProgress=0
4. `handlePressOut()` → holdCompleteFiredRef=false, holdProgress=0 → no segment
✓ Correct: no spurious callback

### Pattern 2: Hold complete THEN release
1. Press-in → holdProgress starts
2. Advance to 3000ms → holdProgress=1
3. `handleHoldComplete()` → holdCompleteFiredRef=true, onReleaseSegment('push')
4. User releases → `handlePressOut()` → ref=true → returns early
✓ Correct: exactly one 'push' callback

### Pattern 3: Hold complete called TWICE
1. Press-in → holdProgress starts
2. Advance to 3000ms
3. `handleHoldComplete()` → ref=false, sets ref=true, emits 'push'
4. `handleHoldComplete()` again → ref=true → returns early
✓ Correct: only one 'push' callback

### Pattern 4: Cancel + partial + release + new press
1. Press-in → holdProgress starts
2. Advance to 500ms → holdProgress ≈ 0.167
3. `cancelAffordances()` → holdProgress=0, pressProgress=0
4. `handlePressOut()` → ref=false, holdProgress=0 → no segment
5. `handlePressIn()` → ref=false, holdProgress restarts from 0
✓ Correct: fresh start, no carryover
