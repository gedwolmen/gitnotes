## Scope
Harden AppFloatingGitButton action and navigation feedback:
- Stage/commit/push dispatch sequentially at most once per release
- Partial push reports failures and navigates to each conflict target without duplicate navigation
- Tap navigation preserves pending Explore selection
- Failed operations leave button usable (no lock stuck)
- No DEBUG toast/logging remains

## Problem Analysis

### Missing operation lock
The original `handleReleaseSegment` had no guard against concurrent calls. If the user
rapidly tapped or if a previous operation was still running when a new release occurred,
multiple stage/commit/push sequences could execute simultaneously, causing race conditions.

### No failure-safe cleanup
If an error occurred during the sequence (e.g., stage succeeds but commit fails, or
commit succeeds but push fails), the operation would complete but the button state
would not be properly reset for the next interaction.

### Potential duplicate conflict navigation
When iterating through `pushResult.failures` and navigating to conflict targets, if
multiple failures had the same `repoId` (e.g., same repo failed for different reasons),
the navigation would be called multiple times for the same target.

## Solution

### 1. Operation lock with `isOperationActiveRef`
Added `const isOperationActiveRef = useRef(false)` to track whether an operation is
currently in progress.

Modified `handleReleaseSegment` to:
- Return early if `isOperationActiveRef.current` is true
- Set `isOperationActiveRef.current = true` before starting the sequence
- Always release in `finally` block: `isOperationActiveRef.current = false`

### 2. Try/finally for guaranteed cleanup
Wrapped the entire operation sequence in a `try { ... } finally { isOperationActiveRef.current = false }`
block. This ensures:
- If stageAllPending throws → lock is released
- If commitAll throws → lock is released
- If pushAll throws → lock is released
- If navigation throws → lock is released

### 3. Conflict navigation deduplication
Changed from direct navigation in a loop to using a Set:
```typescript
const navigatedToConflicts = new Set<string>();
for (const failure of pushResult.failures) {
  if (!navigatedToConflicts.has(failure.repoId)) {
    navigatedToConflicts.add(failure.repoId);
    navigation.navigate('ExploreConflict', { repoId: failure.repoId });
  }
}
```

### 4. Removed unused variable
Removed `pushFailureRepoIds` variable that was declared but never used after the
deduplication change.

## Behavior Contract

### Sequential dispatch (at most once per release)
- User presses and holds → `handleReleaseSegment` is called with segment
- If `isOperationActiveRef.current` is true → return early (no action)
- Otherwise set ref=true and proceed with stage/commit/push sequence

### Failure-safe cleanup
- Any exception during stage/commit/push/navigation is caught by `finally`
- Lock is always released, leaving button usable for next release

### Conflict navigation deduplication
- Multiple failures for the same repoId result in only one navigation call
- Each unique conflict repoId is navigated to exactly once

### Tap navigation (preserved from Task 5)
- Conflicts: direct navigation to `ExploreConflict`
- Non-conflicts: pending action set + navigate to `ExploreTab`
- ExploreScreen reads pending action and applies section/repo, then clears
