# v1.5.0 App Store Rejection — Crash Analysis

> Apple rejected v1.5.0 (build 59) under **Guideline 2.1.0 — Performance: App Completeness** with 6 attached crashlogs from automated probes on iPhone 15,2 + iPad 15,3 running iOS 26.6.1.

## TL;DR

`useProGate()` (called by `OnboardingScreen` at first launch) invoked `useNavigation()` outside any `NavigationContainer`. The hook threw → React Native's exception manager called `reportFatal` → SIGABRT. **Every fresh launch crashed on the onboarding screen.**

The fix (`c5362e86`) is already on `main`. **The release build was tagged before the fix landed** — build a new version from `main HEAD` and resubmit.

The stack signature above is the proof: RN's exception manager only escalates JS errors it considers fatal, and the error bubbled from a TurboModule invocation — the exact pattern of `useNavigation()` throwing inside a React hook.

## Root cause — file-by-file

### `src/hooks/useProGate.ts` (v1.5.0, tagged at `b21d5ef5`)

```ts
export function useProGate() {
  const isPro = useProStore(selectIsPro);
  const status = useProStore((s) => s.status);
  const navigation = useNavigation<NativeStackNavigationProp<RootStackParamList>>();
  // ↑ throws unconditionally if no <NavigationContainer> is in the tree above
  ...
}
```

`useNavigation()` from `@react-navigation/native` is documented to throw when called outside a `NavigationContainer`. v1.5.0 had no guard.

### `App.tsx:149-163`

```tsx
if (showOnboarding) {
  return (
    <SafeAreaProvider>
      <ThemeProvider>
        <NativeWindThemeProvider>
          <StatusBar style="auto" />
          <OnboardingScreen
            onComplete={handleOnboardingComplete}
            onSkip={handleOnboardingSkip}
          />
        </NativeWindThemeProvider>
      </ThemeProvider>
    </SafeAreaProvider>
  );
}
```

`<OnboardingScreen>` is rendered with `SafeAreaProvider` + `ThemeProvider` + `NativeWindThemeProvider` only — **no `NavigationContainer`**. Every first launch hits this branch.

### `OnboardingScreen.tsx:70` calls `useProGate()`

```tsx
const { isPro, openPaywall } = useProGate();
```

OnboardingScreen is the very first interactive screen the user (or App Store reviewer's automated probe) sees.

### Crash sequence

1. App launches → `App.tsx` reads `showOnboarding` from storage → returns the `showOnboarding` branch.
2. React mounts `<OnboardingScreen>`.
3. `OnboardingScreen` calls `useProGate()`.
4. `useProGate` calls `useNavigation()`.
5. **No `<NavigationContainer>` is in the tree** → `useNavigation()` throws synchronously inside the hook.
6. React's error path catches it and surfaces to `RCTExceptionsManager.reportException` (the global TurboModule error reporter).
7. The error is considered fatal (unhandled in a render-phase hook).
8. `reportFatal` calls `objc_exception_throw`.
9. C++ runtime terminates → `abort()` → **SIGABRT**.

Repeat for every reviewer probe on every device — that's the 6 crashlogs.

## Why main HEAD doesn't have the bug — `c5362e86`

Commit `c5362e86 fix: navigation crash, multi-host explore, and large repo OOM` (merged Aug 22 02:04 +0530, **before** v1.5.0 tag at 04:09 +0530) added a `useIsInNavigationContext()` guard + lazy navigation via `useRef`:

```ts
function useIsInNavigationContext(): boolean {
  try {
    useNavigation<NativeStackNavigationProp<RootStackParamList>>();
    return true;
  } catch {
    return false;
  }
}

export function useProGate() {
  const isPro = useProStore(selectIsPro);
  const status = useProStore((s) => s.status);
  const isInNavigation = useIsInNavigationContext();
  const navigation = useRef<NativeStackNavigationProp<RootStackParamList> | null>(null);

  if (isInNavigation && !navigation.current) {
    // eslint-disable-next-line react-hooks/rules-of-hooks
    const nav = useNavigation<NativeStackNavigationProp<RootStackParamList>>();
    navigation.current = nav;
  }
  ...
}
```

The `try/catch` swallows the `useNavigation()` throw on the first call (when OnboardingScreen is mounted outside any container). `isInNavigation` returns `false`, the conditional `useNavigation()` is skipped, the hook returns `{ isPro, status, loading, openPaywall }` and the render continues.

**v1.5.0 was tagged at `b21d5ef5`, which is on the merge commit for PR #919 — a different branch that didn't include `c5362e86`.** The release pipeline picked up a commit ancestry that predates the fix.

   - `5aad2cbd`-`fb38dbec` — 5 clone-perf patches + test fixture fix.

   - `ebf3fd6a`-`eb768806` — E2E harness scaffolding + wiki page.

3. **Submit to App Store.** Reference the new build in Resolution Center and ask for re-review.

## Follow-up: harden the guard

The `c5362e86` fix works in practice but is fragile (a `useNavigation()` inside `try/catch` is a Rules-of-Hooks smell; the `eslint-disable-next-line react-hooks/rules-of-hooks` suppresses the very rule the guard depends on). If the component's mount context ever changes between renders (e.g., OnboardingScreen remounts inside a container after some future refactor), React will throw "Rendered more hooks than during the previous render".

Recommended improvements (any one is sufficient):

- **(a) Move `<OnboardingScreen>` inside `<NavigationContainer>`.** Simplest, removes the need for the guard entirely.
- **(b) Split `useProGate` into two hooks** — `useProGateStatus()` (just `selectIsPro` + `status`, no navigation) and `useProGateNav()` (adds navigation). OnboardingScreen calls only `useProGateStatus()`; paywall callers flows only calls the nav version.
- **(c) Replace `try/catch useNavigation` with a small `<NavigationAvailable.Provider>`** so OnboardingScreen's mount explicitly opts out of the navigation context.

Not blockers for the App Store resubmit; should be addressed before the next release.
